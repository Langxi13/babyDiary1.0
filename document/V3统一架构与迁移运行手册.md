# V3 统一架构与迁移运行手册

## 目标

V3 是一次性统一后的运行时：账户、空间、日记、媒体、相册、AI、通知、同步和后台作业使用同一套 UUID 公共标识和模块化 Spring Boot 入口。V3 不兼容旧 API、旧表或旧版 `/images/**` 媒体 URL；兼容要求只存在于一次性迁移工具，不进入业务代码。滚动部署前已签发的 V3 短时媒体 URL 可在自身有效期内继续读取，不构成旧运行时兼容层。

## 统一结果

- 运行入口：`com.langxi.babydiary.v3.BabyDiaryV3Application`
- 当前 API：`/api/v3/**`
- 当前数据库：独立 `baby_diary_v3`，Flyway 使用 `V1__clean_schema.sql` 和 `V2__media_security_and_lifecycle.sql`
- 公共 ID：`BINARY(16)` 存储、UUID 字符串传输
- 媒体：`media_asset` 加 `diary_media`、`album_media`、`favorite_media`、`user_avatar` 和封面资产外键；`variant_type + profile` 唯一标识物理变体，资产具有 READY、DELETE_PENDING、DELETED 生命周期
- 认证：15 分钟访问令牌、30 天旋转刷新会话、短期二次验证
- 缓存：Redis 共享限流/缓存，Redis 不可用时使用有界本地降级
- 后台任务：原子领取、重试、失败记录和陈旧任务恢复
- 对象存储：LOCAL 和 S3 provider registry，按变体 provider 读取；媒体处理与存储 GC 均幂等且单线程受控
- 导出：V3 ZIP 便携归档、PDF 和 EPUB

旧库的 V1-V15 结构、旧 `diary_image`/`album_photo`/`favorite_photo` 关系、旧对象目录和旧 API 仅由迁移与回滚过程识别，V3 业务请求不会读取它们。

## 迁移前门禁

必须满足以下条件才开始正式切换：

1. 工作区已提交或已明确记录待发布改动，构建机和生产机不要并发运行高负载任务。
2. `mvn -q verify`、前端单测、前端构建和目标 E2E 全部通过。
3. 生产旧服务健康，源库只读预检通过，所有本地媒体对象存在且可读。
4. 磁盘至少保留 2 GiB 空闲；迁移目标库和中间日志不应挤占系统空间。
5. 已执行 `scripts/backup.sh` 并通过 `scripts/verify-backup.sh`，备份已复制到服务器外。
6. 已准备独立的空目标库和最小权限业务账号，不复用旧库连接。

## 影子迁移

生产切换前，使用与生产相同的 Jar、迁移参数和对象目录，在隔离库完成两次迁移。两次输出的业务数据转储 SHA-256 必须一致，迁移报告必须无失败项。影子服务需至少验证：

- Actuator 返回 `UP`；
- 未认证 Profile 返回 `401`；
- 合成账户登录、空间列表、日记创建/详情和相册组读取成功；
- 日记、媒体、相册、收藏、头像、纪念日封面关系无跨空间引用；
- 旧原图 SHA-256、缩略图和关系数量与源库一致。

影子数据库和服务停止后再删除；不要将影子数据目录、日志、账号或测试密钥提交到 Git。

## 正式迁移步骤

### 1. 停止写入并备份

```bash
systemctl is-active diary-backend
scripts/backup.sh
scripts/verify-backup.sh backups/<timestamp>
systemctl stop diary-backend
```

停服后重新确认源库行数和对象目录没有异常变化。不要在迁移过程中让旧应用继续接受请求。

### 2. 创建目标库

目标库必须为空，字符集使用 `utf8mb4`。应用账号只需要目标库上的建表、索引和业务 DML 权限，迁移过程使用同一业务账号即可；生产不要给应用账号全局权限。

### 3. 执行迁移

将源库和目标库连接信息通过环境文件或进程环境注入，不把密码放在命令参数、日志和终端回滚记录中：

```bash
export V3_SOURCE_URL="$DB_URL"
export V3_SOURCE_USER="$DB_USERNAME"
export V3_SOURCE_PASSWORD="$DB_PASSWORD"
export V3_TARGET_URL="$V3_DB_URL"
export V3_TARGET_USER="$V3_DB_USERNAME"
export V3_TARGET_PASSWORD="$V3_DB_PASSWORD"
export V3_OBJECT_ROOT="$DIARY_OBJECT_PATH"

scripts/v3-migrate.sh preflight
export V3_MIGRATION_CONFIRM=MIGRATE_TO_V3
scripts/v3-migrate.sh migrate
scripts/v3-migrate.sh verify
```

`preflight` 是只读检查；`migrate` 要求目标库为空并再次检查确认值；`verify` 比较源/目标语义数量、空间边界、UUID 映射、媒体存在性、原图校验和、相册关系、收藏和封面资产，并拒绝任何没有 READY 原图变体的 READY 媒体。迁移后的原图 profile 应保持 `source`，缩略图等派生资源保持 `default`，不要通过改库把两者强行归一。任何失败都必须停止切换。

### 4. 切换配置并部署

将以下非秘密配置写入 `/etc/baby-diary/backend.env`：

```bash
V3_DB_URL=jdbc:mysql://127.0.0.1:3306/baby_diary_v3
V3_DB_USERNAME=baby_diary_app
V3_DB_PASSWORD=<private>
MYSQL_DATABASE=baby_diary_v3
```

随后执行：

```bash
scripts/deploy.sh
scripts/health-check.sh
```

健康检查通过后，使用既有账户完成最小生产冒烟：登录/刷新、空间列表、日记列表和详情、相册首页和详情、头像、纪念日、草稿、AI 报告历史和原生 bootstrap。生产不要自动批量创建测试数据。

## 回滚

以下任一情况都是阻断项：启动失败、Flyway 失败、迁移校验不一致、跨空间数据可见、日记/媒体/相册无法读取、登录失败或出现持续 5xx。

1. 停止 V3 服务并保留目标库、日志和迁移报告。
2. 将 systemd drop-in 恢复为旧服务配置，恢复旧 Jar。
3. 将私有环境中的数据库连接恢复为旧 `DB_URL`，并确保旧媒体目录仍在原位置。
4. 启动旧服务、执行旧版本健康检查和只读业务冒烟。
5. 重新核对旧库和旧媒体数量，不在生产库执行未经验证的反向 SQL。

旧库、旧媒体目录、上一版 Jar 和切换前备份至少保留 14 天；观察期结束前不执行清理。

## 清理与长期维护

观察期结束后，先确认：外部备份可恢复、V3 全量备份已生成、所有客户端已升级、Nginx 没有旧图片路由、日志和监控没有旧 API 请求。然后再分阶段删除旧 Jar、旧目录和旧库。

统一后的新增功能必须遵守：

- 新接口只能放在 `/api/v3`，不重新引入 `/api/v2` 适配层。
- 新媒体只能通过 `media_asset` 和类型明确的关系表关联。
- 新的媒体读取和签名调用必须显式携带查询所得 profile，不得固定假设 `profile=default`。
- 新的媒体签名必须携带 HMAC 保护的访问上下文 ticket、实际 profile 和过期时间；旧的无上下文签名必须拒绝。
- 媒体内容接口必须保留 GET/HEAD、单段 Range、ETag/304、416 和受保护内容 no-store 语义。
- 跨空间查询必须先校验成员关系，再读取业务对象。
- 长任务进入 `background_job`，必须具备幂等键、最大重试次数、失败状态和陈旧任务回收。
- 业务缓存键包含账户/空间作用域，登录退出和切换账户时前端必须清理并隔离缓存。
- 文档、测试夹具和 E2E 必须使用 V3 路径及合成数据。
