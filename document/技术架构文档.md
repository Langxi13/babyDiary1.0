## 系统架构概述

### 整体架构

Baby-Diary系统采用前后端分离架构，后端只提供RESTful API服务，前端由Nginx托管Vue/Vite构建产物。

```
┌─────────────────┐         HTTP/HTTPS         ┌─────────────────┐
│   前端应用      │ ◄─────────────────────────► │   后端服务      │
│  (Vue 3 + Vite) │                             │ (Spring Boot)   │
└─────────────────┘                             └─────────────────┘
         │                                               │
         ▼                                               ▼
┌─────────────────┐                             ┌─────────────────┐
│   浏览器        │                             │   MySQL 数据库   │
│  (用户界面)     │                             └─────────────────┘
└─────────────────┘                                      │
                                                        ▼
                                               ┌─────────────────┐
                                               │ Redis 缓存      │
                                               └─────────────────┘
```

### 架构特点

1. **前后端分离**：前端和后端完全独立开发、部署和维护
2. **RESTful API**：后端提供标准的RESTful接口
3. **混合会话认证**：短期 JWT 负责接口认证，服务端保存并轮换刷新会话
4. **模块化分层**：后端按业务模块组织 `api/application/domain/infrastructure`，application 通过仓储/网关端口访问基础设施
5. **REST-only**：旧Thymeleaf页面和后端模板Controller已移除
6. **移动端 App Shell**：Vue 前端在手机宽度下由全局 Shell 统一提供顶部栏、底部主导航和安全区布局，页面只负责业务内容
7. **原生图片入口**：Capacitor 客户端在上传区域直接调用系统相册或相机，Web/PWA 使用标准文件选择控件
8. **空间化数据模型**：个人空间与共同空间共用 V3 日记、协作、同步、媒体和 AI 能力
9. **离线优先写入**：IndexedDB 保存待同步操作，服务端以幂等操作 ID 和版本号处理冲突
10. **统一媒体存储**：所有媒体进入 `media_asset` 和 typed relations，使用私有本地目录或 S3/COS 兼容对象存储及短时签名 URL；V3 运行时不读取旧版路径

### 构建与拆包

前端页面通过 Vue Router 懒加载。日记编辑页使用 Tiptap，相关 ProseMirror 代码只进入 `DiaryForm` 路由 chunk，不进入首页首屏预加载。Element Plus 组件按页面局部引入，避免全量 UI 库进入主包。桌面导航 hover、手机导航 touchstart 时会预加载目标路由 chunk，降低首次切换页面的等待时间。

前端 API 层提供内存 TTL 缓存和同 key 请求去重。列表、首页、相册和草稿默认缓存 30 秒，时间轴和日历默认缓存 2 分钟，标签和纪念日默认缓存 10 分钟；创建、更新、删除、收藏等写入操作会失效相关缓存。所有缓存键自动增加当前用户作用域，日记、相册和纪念日还区分 standard/elevated 访问级别；elevated 响应只参与当前并发请求合并，不写入缓存。二次验证建立或过期时立即清空内存缓存。缓存和 HTTP 请求同时记录客户端会话 generation：退出、登录其他账号或跨标签页身份变化时统一递增 generation、清空缓存和认证相关 Store；旧请求、旧刷新操作完成后会作为取消请求丢弃，不能写入新会话。会话重置还会中止在途刷新请求，同一标签页的新登录会等待服务端登出完成，避免旧响应覆盖新账号的刷新 Cookie。共同空间离线数据按账户隔离；写入 IndexedDB 的锁定日记强制降为无正文、心情、标签和媒体的占位。

Web Axios 与 Capacitor HTTP 使用同一响应契约：成功请求直接返回后端 JSON body，不构造 `{ code, message, data }` 包装。API 方法的空间参数必须由 Store 或页面边界显式传入，不能在 API 模块内读取 `localStorage` 猜测当前空间。前端业务对象只使用后端规范字段 `id`、`diaryDate`、`contentHtml`、`mood` 和 `representations`；短时签名 URL 只在内存中补全，写入 IndexedDB 前会递归移除。

敏感操作通过 `stepUp.js` 复用一个挂载在应用根节点的 `StepUpDialog`。调用方只等待验证 Promise，不直接依赖具体 UI 组件；弹窗负责并发请求合并、密码提交、原位错误、取消和会话重置。认证 API 在弹窗打开后动态加载，避免将低频认证管理代码并入首屏主包；步骤验证请求使用局部静默错误配置，由弹窗呈现可恢复错误，访问令牌失效等全局认证处理仍由统一响应拦截器接管。

页面级 SCSS 从 `DiaryForm`、`AiReports`、`Anniversaries`、`Album`、`AlbumDetail`、`DiaryList`、`Timeline`、`Home` 和移动壳组件中拆出到独立样式文件。日记图片选择、排序、预览、原生文件接入和更新参数集中在 `useDiaryImages` composable；个人与共同空间共用 `DiaryMoodPicker` 和 `DiaryMediaGallery`，避免心情排版和媒体 representation 解析形成两套实现。全局按钮和页面过渡只声明实际变化的 CSS 属性，不使用 `transition: all` 触发布局无关动画。

`frontend/src/assets/styles/mobile-foundation.scss` 作为手机端公共布局层，集中定义顶部栏、底部栏、页面边距、表面颜色和控件圆角变量。在 `768px` 及以下统一提供安全区内边距、最小 `320px` 布局基线、横向溢出保护、输入控件 16px 字号与至少 44px 触控高度，并约束 Element Plus 的对话框、消息、确认框、日期面板和下拉面板不超出动态视口。页面样式只保留各业务区域自身的网格和视觉层级，减少重复的移动端基础规则。

### PWA、Capacitor 与移动壳能力

`frontend/public/manifest.webmanifest` 只提供安装元数据、图标和启动信息，不注册系统分享目标。`frontend/public/sw.js` 负责应用壳更新与离线导航回退：普通 GET 只缓存同源成功响应，网络失败时只有页面导航请求回退到 `index.html`，接口、图片、失败响应和静态资源失败不会错误写入缓存或返回 HTML。

`MobileAppShell` 将手机端顶部栏、五项主导航和次级功能抽屉与桌面 `NavBar` 分离。桌面导航从共享入口配置中展示首页、日记、空间、相册和写日记，其余功能进入“更多”菜单；主导航和抽屉入口在触摸开始时预加载路由 chunk。抽屉打开时锁定页面滚动并支持 Escape 关闭。壳层监听 `visualViewport` 高度变化，识别软键盘后隐藏底部导航，避免导航遮挡输入区。日记列表把移动筛选拆分为独立的 `DiaryMobileFilters` 组件：搜索框常驻，日期、标签和心情使用互斥展开面板，日期继续使用两个纵向单日期选择器，避免双日历面板在窄屏并排溢出。

Vue Router 使用统一 `scrollBehavior`：普通前进导航回到页面顶部，历史返回优先恢复 `savedPosition`。因此从列表打开日记详情时顶部编辑、删除操作立即可见，返回后仍保留用户原来的列表浏览位置。

Capacitor 8 客户端复用同一套 Vue 路由和组件；原生环境使用 hash history，首次启动进入 `ServerSetup`，只把通过 `/api/v3/client/bootstrap` 验证的 HTTPS 根地址保存在 Capacitor Preferences。远端图片 URL 由 `runtimeConfig` 统一补全，Web/PWA 继续使用相对路径。切换服务器会先清除访问令牌、账号信息、API 缓存、IndexedDB 离线队列和原生 Cookie，避免跨服务器复用旧会话。

原生登录、刷新和退出使用 `CapacitorHttp`，刷新令牌仍由后端以 `Secure`、`HttpOnly` Cookie 管理；普通 JSON 与 multipart 业务请求继续走 Axios 和 Bearer Token。Android WebView 来源固定为 `https://localhost`，iOS 为 `capacitor://localhost`，后端只允许这两个明确来源。Nginx 对普通资源保持 `Cross-Origin-Resource-Policy: same-origin`，仅对短时签名媒体路径返回 `cross-origin`，使原生 WebView 可以显示图片而不放宽其他资源。

`NativeImageActions` 封装系统相册和相机，覆盖日记、头像、纪念日封面和共同空间图片入口。受支持的 JPEG、PNG、GIF、WebP 保留格式；HEIC/HEIF 等格式使用原生 JPEG 预览或 Android 解码转码后上传。Android Manifest 不注册 `ACTION_SEND` 或 `ACTION_SEND_MULTIPLE`，用户在上传页面内直接选择图片。应用关闭系统备份和设备迁移，媒体不会写入公共外部存储。

Android 工程位于 `frontend/android`，使用 JDK 21、SDK 36、单 Gradle worker 和无常驻 daemon；后端继续使用 JDK 17。CI 生成 Debug APK，Release 工作流从 GitHub Secrets 读取固定 JKS，并与 `config/android-release-cert.sha256` 中的公开证书指纹比对。签名材料由仓库外私有文件生成并纳入受校验备份，源码和构建日志均不包含密码或私钥。

`config/release-version.properties` 是产品版本和 Android 构建号的单一来源，后端 bootstrap、Vite、Android Gradle、本机构建脚本和 CI 均读取该文件，使 `PRODUCT_VERSION` 与 `ANDROID_VERSION_CODE` 进入同一次 Git 审查。`build-android-release.sh` 和 CI 共用 `verify-android-artifact.sh` 校验 APK v2 签名、AAB 签名、包名、版本、minSdk 24、targetSdk 36、关闭备份、禁止明文流量以及 Capacitor 不内置服务器地址。工作流使用不可变标签发布 APK、AAB 和 SHA-256 校验和；同一证书与递增 `versionCode` 构成 Android 覆盖升级边界。iOS 依赖已锁定，平台工程、签名和真机验收等待 Mac/Xcode 环境完成。

`ClientReleaseService` 将服务器发布配置转换为 `/api/v3/client/bootstrap` 中的 Android 更新清单。直接分发只接受 HTTPS 或经过规范化的同源路径，并要求合法版本号和完整 SHA-256；无效配置降级为 `enabled=false`。前端 `appUpdate` Store 使用 `App.getInfo()` 读取实际安装包的 `versionName/versionCode`，原生壳启动后只检查一次并在有新版本时显示非模态提示。“关于与更新”页面通过 Capacitor Browser 打开下载地址，由浏览器下载、Android 系统签名校验和用户安装确认共同完成更新；应用没有静默安装能力。

`publish-android-update.sh` 在本地签名构建完成后再次调用统一制品验证器，把 APK 原子发布到同源 `deploy/frontend/downloads/android/`，计算 SHA-256 并生成 `/etc/baby-diary/android-update.env`。systemd 独立 drop-in 加载该非秘密配置，网页部署通过 `rsync --exclude downloads/` 保留已经发布的安装包，避免部署后更新链接失效。

Web/PWA 使用标准文件选择入口，Capacitor 使用原生相册与相机入口。共同空间编辑器另使用 IndexedDB 保存离线日记和媒体队列，并通过 V3 sync pull/push 接口增量同步。

生产敏感配置不写入仓库。默认配置位于 `backend/src/main/resources/application.yml`，生产覆盖配置位于 `config/application-prod.yml`，真实密钥和数据库连接从 `/etc/baby-diary/backend.env` 注入。生产 Java 进程使用专用系统用户 `baby-diary` 运行，数据库连接使用最小权限业务账号，不使用 root 作为应用运行账号。

## 数据库设计

### 数据库表结构

Flyway 使用 `backend/src/main/resources/db/migration/V1__clean_schema.sql` 作为结构基线，并通过连续版本迁移演进。业务表使用自增内部主键配合 `BINARY(16)` 公共 UUID；API、前端和跨空间数据边界只使用公共 UUID，不向客户端暴露内部自增 ID。

| 分组 | 核心表 | 作用 |
| --- | --- | --- |
| 身份 | `account`、`auth_session`、`account_token`、`recovery_code` | 账户、30 天刷新会话、邮箱恢复和一次性恢复码 |
| 空间 | `diary_space`、`space_member`、`space_invitation`、`tag` | 个人/共同空间、成员角色、邀请和标签 |
| 日记 | `diary`、`diary_revision`、`diary_comment`、`diary_reaction`、`diary_media` | 正文、版本、互动和有序媒体关系 |
| 媒体 | `media_asset`、`media_variant`、`album_media`、`favorite_media`、`user_avatar` | 统一资产、派生表示、相册、收藏和头像 |
| 体验 | `album_group`、`album`、`anniversary`、`diary_draft`、`diary_template` | 相册、纪念日、草稿和模板 |
| AI 与平台 | `ai_config`、`ai_report`、`space_ai_schedule`、`notification`、`reminder`、`sync_change`、`sync_retention`、`private_share` | AI、通知、提醒、同步和私密分享 |
| 管理与作业 | `system_invitation_config`、`background_job`、`outbox_event` | 加密邀请码、可重试作业和事务事件 |

统一媒体关系为 `diary_media(diary_id, asset_id, sort)`、`album_media(album_id, asset_id, sort)`、`favorite_media(account_id, asset_id)` 和 `user_avatar(account_id, asset_id)`；`album.cover_asset_id` 与 `anniversary.cover_asset_id` 直接引用 `media_asset`。V3 不保留第二套业务媒体表。

### 数据库关系

- account (1) ----< (N) auth_session / account_token / recovery_code
- account (N) >----< (N) diary_space，通过 space_member 关联
- diary_space (1) ----< (N) diary / tag / media_asset / notification / reminder
- diary (1) ----< (N) diary_revision / diary_comment / diary_reaction / diary_media
- diary (N) >----< (N) media_asset，通过 diary_media 关联
- album (N) >----< (N) media_asset，通过 album_media 关联
- account (1) ----1 user_avatar ----1 media_asset
- diary_space (1) ----< (N) ai_report / space_ai_schedule / private_share / sync_change

旧库迁移链和一次性迁移程序已从运行时移除。生产结构只由当前 `db/migration` 中的 Flyway 迁移管理，已执行迁移不得修改。

### 查询与缓存优化

- 日记列表、时间轴和草稿列表只读取正文摘要；详情、编辑和单份草稿接口仍读取完整正文。
- 日记列表和时间轴按当前结果 diaryId 批量查询标签和图片，避免每篇日记单独查询。
- Flyway 执行 `db/migration` 中的连续版本迁移，发布前校验 checksum 并完成升级测试。
- 通用照片、系统相册和自建相册详情提供数据库 `LIMIT/OFFSET` 分页；相册首批默认24张，元数据和首批照片并行请求，首页收藏预览只读取6张，避免照片量增长后一次返回和解码全部图片。
- `RedisReadCache` 只缓存标签、日历/时间轴/年度洞察聚合和相册元数据；key 固定包含缓存区域、空间 UUID、账户 ID、区域版本和查询摘要，TTL 为2至5分钟。
- 相册缓存写入前移除存储 provider、对象 key 和校验和；授权判断、锁定正文、签名媒体 URL、分享、管理员数据和业务写结果不进入 Redis。
- 写操作通过 `ReadCacheInvalidator` 在事务提交后提升空间级区域版本，不使用全库扫描删除。Redis 异常触发30秒熔断并回源数据库，待恢复的失效请求在下次可用读取前补放。
- 时间轴和日历查询使用日期范围条件，不在 WHERE 中使用 `YEAR(date)` 或 `MONTH(date)`，以便复用日期索引。
- 相册封面回退策略不再使用 `ORDER BY RAND()`，改为按相册照片排序稳定选择已有图片；后续数据规模继续增大时可扩展为持久化 `cover_image_id`。
- 前端只通过统一媒体 `representations` 解析签名地址。列表、相册、首页、时间轴和网页全屏查看器优先读取最长边不超过 1280 像素的 `thumbnail`；派生图缺失或 `sizeBytes` 不小于原图时选择 `original`。导出与原始质量下载固定读取 `original`，避免普通查看重复传输大尺寸原图。
- 日记列表 Store 使用递增请求序号，只允许最后一次筛选请求更新页面；关键词输入使用350毫秒防抖，减少无效查询并避免旧响应覆盖新筛选。
- 分页边界由各模块的响应 record 统一组装，游标分页与页码分页都返回明确的续页元数据。
- `/api/v3/**` 使用有界分页、按空间索引和数据库慢查询观测；相册和 AI 报告不一次加载全部内容，时间轴游标续页使用 `includeTotal=false` 避免重复计数。
- 媒体保护和公共 UUID 批量查询固定按500项拆分 SQL `IN` 条件，并在合并后恢复调用方顺序，避免大型请求触发数据库参数或数据包上限。

## 系统分层架构

### 后端分层

后端模块统一按 `api`、`application`、`domain`、`infrastructure` 组织。application 只依赖仓储/网关端口，MyBatis Mapper 和对象存储等实现位于 infrastructure；API 与 application 均禁止反向依赖 infrastructure，domain 禁止依赖 Spring、MyBatis 和 Servlet。`ArchitectureTest` 会在构建中强制这些边界。

Java 源码使用 Spotless 固定版本格式化，`mvn verify` 执行格式检查。需要批量整理历史代码时使用 `mvn -f backend/pom.xml spotless:apply`，提交前必须再次执行 `spotless:check`，不以手工排版绕过门禁。

## 核心模块设计

### 认证模块

#### JWT认证流程

```
1. 用户提交用户名和密码
2. AuthenticationService 使用 BCrypt 验证密码和账户状态
3. 验证成功后生成15分钟访问令牌和随机刷新令牌
4. 刷新令牌只以 SHA-256 摘要入库，原值写入 HttpOnly Cookie
5. 前端在后续请求 Header 中携带访问令牌
6. 访问令牌过期时，前端调用刷新接口并轮换刷新令牌
7. 前端刷新操作绑定发起时的会话 generation；账号已退出或切换时，旧刷新结果不得恢复凭据
8. AuthenticationFilter 通过 AccessTokenCodec 校验签名、过期时间和用户 tokenVersion
9. 验证通过后设置 SecurityContext 并放行
```

#### 关键类

- `AccessTokenCodec` / `JwtAccessTokenCodec`：访问令牌生成和验证
- `AuthenticationFilter`：Bearer Token 拦截和认证上下文建立
- `SecurityConfig`：安全配置
- `AuthenticationService`：刷新令牌创建、轮换、撤销和设备列表
- `AccountRecoveryService`：邮箱令牌、密码找回和恢复码
- `StepUpService`：短期二次验证令牌签发和校验

### 日记管理模块

#### 创建日记流程

```
1. 前端先通过 MediaController 上传媒体
2. MediaService 校验文件签名、尺寸和空间额度，并写入私有 ObjectStorage
3. 后台 MEDIA_PROCESS 作业生成缩略图、海报、波形或转码表示
4. 前端向 DiaryController 提交正文、标签和有序 mediaIds
5. DiaryService 在事务中写入 diary、diary_tag、diary_media、修订和同步/Outbox 事件
6. Controller 使用 MediaRepresentationService 返回短时签名 URL
```

### 图片管理模块

#### 图片存储

- 存储位置：`DIARY_OBJECT_PATH` 指定的私有对象根目录，后续可替换为 S3/COS
- 原图对象键格式：`v3/media/{spaceUuid}/{assetUuid}/original/source`，不包含用户名或客户端原始文件名
- 派生对象键包含随机 UUID 和表示类型，竞争任务不会覆盖已有对象
- 支持格式：JPEG、PNG、GIF、WebP
- 文件大小限制：图片25MB、音视频256MB
- 校验方式：同时校验允许的 MIME 和文件签名，不接受 SVG 或伪造图片类型
- 生命周期规则：上传失败释放额度并清理对象；删除先进入 `DELETE_PENDING`，由幂等 `STORAGE_GC` 作业删除对象并释放额度
- 关系规则：从日记/相册移除只删除 typed relation，不删除 media_asset；资产删除是单独的显式操作
- 访问规则：`MediaService` 生成短时签名 URL，锁定媒体仍需二次验证
- 导出规则：ZIP 临时文件在响应流关闭后自动删除

### AI报告模块

#### 生成流程

```
1. 前端选择周报、月报或年报周期，或由空间定时任务触发
2. AiController 校验登录用户和请求参数
3. AiReportService 解析周期，并查询个人或空间在该周期内的可用日记
4. 批量补充日记标签，仅整理日期、标题、文字内容、心情和标签
5. 锁定日记在查询层排除，OpenAiCompatibleClient 调用配置的 /chat/completions 接口
6. 生成 Markdown 报告并写入 ai_report
7. 前端展示报告，并可在历史报告中再次查看或删除
```

#### 配置方式

- 使用 OpenAI 兼容 Chat Completions 风格配置：`baseUrl`、`model`、`apiKey`、`timeoutSeconds`。
- `baseUrl` 填写到版本路径，例如 `https://api.openai.com/v1`，后端自动拼接 `/chat/completions`。
- `apiKey` 只在保存时提交明文，后端使用 `AI_CONFIG_ENCRYPTION_KEY` 派生 AES-GCM 密钥加密后存库，读取配置时只返回脱敏状态。
- AI 输入不包含图片文件、图片地址或图片识别内容。

## 安全设计

### 认证安全

1. **密码加密**：使用Spring Security的BCrypt加密算法
2. **访问与刷新会话**：
   - 使用HMAC-SHA256签名算法
   - V3 访问令牌默认15分钟，刷新会话默认30天并单次轮换
   - JWT 包含用户ID、用户名和 tokenVersion；修改密码会使旧令牌失效
   - 刷新令牌、邮箱令牌和二次验证令牌仅以摘要存储
3. **日记锁**：密码二次验证令牌默认5分钟，派生数据和同步载荷同步脱敏
4. **邀请码注册**：全局邀请码使用独立环境密钥派生的 AES-256-GCM 密钥加密存库；注册事务读取当前密文并恒定时间比较，轮换提交后旧码立即失效
5. **管理员查看**：邀请码明文接口同时要求 `ROLE_ADMIN` 和短期二次验证令牌，响应禁止缓存且不记录明文日志

### 接口安全

1. **CORS配置**：生产环境只允许 `CORS_ALLOWED_ORIGINS` 中明确配置的来源
2. **权限控制**：用户只能访问和操作自己的数据
3. **参数校验**：Controller 使用 Jakarta Validation，application 用例继续校验跨字段规则、日期范围、媒体数量和分页上限；日记与 AI 报告每页最多50条，相册每页最多60条
4. **SQL注入防护**：使用MyBatis参数化查询
5. **健康检查最小暴露**：Actuator 仅开放 `/actuator/health`；Nginx 使用精确 location 代理到回环后端，发布探活同时校验 JSON 类型和顶层 `status=UP`，不接受 SPA fallback 的伪 200
6. **管理接口**：AI 配置和系统邀请码只允许 ADMIN；邀请码查看和轮换额外要求密码二次验证；生产 Swagger/OpenAPI 默认关闭
7. **限流**：登录、刷新、找回密码、恢复码和私密分享入口按来源与身份限流
8. **网络边界**：生产 Java 服务只绑定 `127.0.0.1:10002`，公网流量必须经过提供 TLS、安全头和静态资源服务的 Nginx
9. **运行隔离**：systemd 通过 `PrivateTmp=true` 隔离 Tomcat 临时目录；部署前验证主机 `/tmp` 为 `1777`、服务用户可写，并拒绝把 `/tmp`、`/var` 等共享系统目录作为图片数据父目录

### 文件上传安全

1. **文件类型校验**：V3 支持 JPEG、PNG、GIF、WebP、MP3/M4A/OGG/WAV、MP4/WebM/MOV，并校验真实文件签名
2. **文件大小限制**：V3 业务上传默认最大100MB，反向代理和请求总大小上限为300MB
3. **文件名安全**：使用 UUID 随机文件名，不保留用户名和客户端原始文件名；所有路径都限制在上传根目录内
4. **目录权限**：统一对象属于 `baby-diary:baby-diary`，目录为 `0700`、文件为 `0600`；Nginx 不直接读取媒体文件
5. **资源归属**：手动相册和 AI 相册确认前都会重新校验 assetId 的用户、个人空间、媒体类型和锁定状态
6. **私有对象隔离**：`DIARY_OBJECT_PATH` 是本地媒体唯一根目录；COS/S3 接入也必须保持私有桶和最小权限
7. **签名访问**：统一媒体 URL 包含资源、变体和过期时间签名，默认短时有效；锁定媒体在签发前要求二次验证

### AI配置安全

1. **密钥加密存储**：API Key 使用 AES-GCM 加密后写入 `ai_config.encrypted_api_key`
2. **环境密钥注入**：生产加密主密钥来自 `/etc/baby-diary/backend.env` 的 `AI_CONFIG_ENCRYPTION_KEY`
3. **前端不回显明文**：配置读取接口只返回是否已配置和脱敏占位
4. **最小化发送内容**：报告生成只发送必要日记文字元数据，不发送图片内容
5. **连接地址约束**：Base URL 只接受 HTTP/HTTPS 且不能包含账号、查询参数或片段；下游异常详情只写入受控日志，不直接回传前端

### 错误处理

- 统一异常处理：`ApiExceptionHandler`
- 业务异常：`ApiException`
- 错误响应：`ApiExceptionHandler` 统一生成 RFC 9457 Problem Detail 和稳定业务 code；映射阶段的 405/406/415、缺失 multipart、上传过大和唯一键竞争不会落入无说明 500

## 质量保障架构

项目按脚本治理、单元/组件、真实 MySQL 集成、三浏览器 E2E、打包预发布和生产冒烟分层验证。`scripts/verify.sh` 聚合脚本、后端和前端门禁；Playwright 使用 MySQL 8.4、Redis 与仓库内回环 Node AI Mock 隔离运行；`compose.staging.yaml` 使用发布 Dockerfile 验证容器健康、安全头、ZAP 和 k6。脚本测试还覆盖 Nginx 预检顺序、真实 Actuator 状态、systemd 私有临时目录及共享目录权限保护。CI 的第三方 Actions 使用完整提交 SHA 固定，版本注释供 Dependabot 识别和更新，避免可变标签被重写后进入构建链路。

后端 JaCoCo 最低要求为 Lines 45%、Branches 28%；前端 Vitest 最低要求为 Lines 50%、Statements 45%、Functions 30%、Branches 30%。CI 将脚本、后端、前端、E2E、供应链和 DAST 拆为独立任务，周期性能工作流另以 50 个合成用户、峰值 10 VU 验证核心读路径。

测试环境不得加载生产用户数据。AI 自动化只访问仓库内回环 Node Mock，真实提供商仅允许在受控预发布环境通过 `scripts/smoke-ai-provider.sh` 冒烟。完整风险矩阵、真机清单和发布门禁见 [测试与发布验收方案](测试与发布验收方案.md)。
